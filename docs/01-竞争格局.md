## 一、SkillsBench（已存在，必须正面对待）

| 项 | 内容 |
|---|---|
| 论文 | [arXiv 2602.12670](https://arxiv.org/abs/2602.12670) — *SkillsBench: Benchmarking How Well Agent Skills Work* |
| 作者 | Xiangyi Li, Yimin Liu, Wenbo Chen, ... Dawn Song 等（约 80 人，跨机构） |
| 版本 | v1 2026-02-13 → v4 2026-06-14 |
| 代码 | [benchflow-ai/skillsbench](https://github.com/benchflow-ai/skillsbench) — **1,917★** |
| 规模 | **87 个任务 / 8 个领域**，配 curated Skills + **deterministic verifiers** |
| 实验 | **18 组 model-harness 配置**，matched no-Skills vs curated-Skills 两条件 |
| 主结论 | 平均通过率 **33.9% → 50.5%（+16.6pp，归一化增益 25.5%）**；配置级增益 +4.1 ~ +25.7pp |
| 附带结论 | **≤3 个模块的聚焦技能，优于大而全的技能包**；小模型 + 技能可以追平大模型无技能 |

### 它做对了什么（我们要学的）

1. **配对评测（paired evaluation）**，同任务、同模型，只改技能条件。这是唯一正确的方法论。
2. **确定性 verifier**，不靠 LLM 打分，靠可执行验证。这是 A 级评分器的样板。
3. **归一化增益（25.5%）**，与我们 `headroom_closed` 的思路一致。
4. **聚焦技能优于大包**，这个结论本身就是最好的传播素材，说明「技能包不是越多越好」。

### 它缺什么（我们的三个楔子）

| # | 缺口 | 证据 | 我们的做法 |
|---|---|---|---|
| **1** | **没有安慰剂臂** | 原文 "matched no-Skills and curated-Skills conditions"，只有两条件 | 三臂对照，`uplift = treatment − placebo` |
| **2** | **只有 Tier 1，没有通用探针** | 87 个任务是手写的，只能测他们自己配了题和 verifier 的技能 | Tier 0 六探针，任意技能包秒级可测 |
| **3** | **题库封闭，不联邦** | 固定 inventory，不开放提交 | `taskset.json` 开放协议，谁都能交题 |

### 它还缺什么（次要，但可用来做差异）

4. **测的是研究者自建的 curated Skills，不是真实发布的技能包**，所以 `addyosmani/agent-skills` 这种 116k 星的真实包，SkillsBench 测不到。
5. **没有安全维度**，不测注入抗性、隐藏指令、数据外泄。
6. **没有代价维度**，不测 token 开销、延迟、负迁移。
7. **没有可消费的产物**，出论文和榜单，不出「作者能贴进 README 的 badge」。

## 二、我们的定位（一句话）

> **SkillsBench 回答「技能有没有用」。UpliftBench 回答「这个技能到底贡献了多少、代价是什么、安不安全、值不值得装」。**

对应到产品形态：

| 维度 | SkillsBench | UpliftBench |
|---|---|---|
| 本质 | 学术基准 | 生态审计工具 + 协议 |
| 对照 | 两臂 | **三臂（含安慰剂）** |
| 覆盖 | 87 题 / 8 领域 | **任意技能包（Tier 0）** + 联邦题库（Tier 1） |
| 输出 | 论文 + 榜单 | **SkillCard + badge + 协议** |
| 用户 | 研究者 | **技能包作者 + 使用者** |
| 门槛 | 要写题和 verifier | **`uplift probe` 一条命令** |

## 三、其他相关项目（不是竞品，但要引用）

| 项目 | 关系 | 说明 |
|---|---|---|
| `SWE-bench` / `SWE-bench Verified` | 上游方法论 | 配对评测、确定性验证的源头。我们的 taskset 格式参考它 |
| `τ-bench`（tau-bench） | 方法论参考 | 命名与「多轮 + 工具」评测范式 |
| `AgentBench` / `AgentBoard` | 同类 | agent 能力基准，不针对技能包 |
| `GAIA` / `HAL` | 同类 | 通用 agent 能力榜 |
| `NVIDIA/SkillSpector` | **互补，非竞品** | 扫技能包里的 prompt injection / 数据外泄 / 供应链风险。**我们 Tier 0 的探针 4（注入抗性）与它重叠，应当引用它而不是重造** |
| `vercel-labs/skills`（`npx skills add`） | **分发层，可集成** | 它是技能包的安装器。我们的 probe 应该能直接吃它装出来的目录 |
| `litellm` | 无关 | 只做路由，不做质量评测 |

### 与 SkillSpector 的关系要特别处理

它做**静态安全扫描**（SKILL.md 里的恶意模式），我们做**动态行为探针**（装了之后 agent 会不会被劫持）。

**建议：Tier 0 探针 4 直接集成 SkillSpector 作为静态预检，我们只补动态部分。** 这样既省工，又自动获得它的公信力背书。

## 四、时间窗口判断

- SkillsBench v1 是 2026-02，v4 是 2026-06，代码 1,917★，它已经站稳了。
- 但它是**论文项目**，节奏慢，不追生态变化。
- 技能包生态在 2026 年 10–11 月才真正爆发（我们调研的 30 天里 24+ 个技能包上榜）。

**结论：赛道已被验证（好事），但生态侧的空白还开着（机会）。窗口大概 3–6 个月，等到某个大厂或 Vercel 出一个官方审计工具，就关上了。**

**所以第一版必须快，一周内出 Tier 0。**

## 五、如果 SkillsBench 明天加了安慰剂臂怎么办

**这是真实风险，提前想好。**

| 情景 | 应对 |
|---|---|
| 他们加安慰剂臂 | 我们转向「Tier 0 覆盖真实发布的技能包」+「联邦题库」+「作者可自助出 badge」。他们的封闭题库做不了自助服务 |
| 他们开放题库提交 | 我们转向「安全 + 代价」维度，和他们的「效果」维度互补，并主动合并/引用 |
| 大厂出官方工具 | 我们做**跨厂商中立**的那一个。单一厂商的榜天然不可信，这是结构性优势 |

**底线：只要「中立 + 自助 + 覆盖真实包」这三条成立，我们就有位置。**
