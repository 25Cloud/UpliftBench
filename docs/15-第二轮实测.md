# 15 · 第二轮实测（v0.1.1 · web-guidance@1.1.0）

> 这一轮换了三件事：任务集扩到 48 题、技能包换成**语义对口**的 `modern-web-guidance`、`repeats` 提到 5。
> 目的是回答第一轮留下的两个 P0：任务集没有中间难度 · 配对不语义对口。

---

## 一、跑的是什么

| 项 | 值 |
|---|---|
| 任务集 | `web-guidance@1.1.0`（48 题，A 级 tests） |
| 技能包 | `GoogleChrome/modern-web-guidance-src` 的 `guides/`，**真身技能**：1 个 SKILL.md，9.8k token，内容会让 agent 去跑 `npx modern-web-guidance search/retrieve` |
| 模型 | `glm-5.3-flash` |
| harness | `openai-compat`，`--activation auto`（激活与否由模型决定） |
| 臂 | baseline / placebo / treatment |
| repeats | **5** |
| run 数 | 48 × 3 × 5 = **720** |
| 成本 | **$60.63** |
| 墙钟 | p50 37.6s / p95 内部同量级（单任务） |

原始记录：`.uplift/v11/runs.db`。

## 二、主结论（ITT，协议口径）

| 臂 | 通过率 |
|---|---|
| baseline（不装） | **73.8%** |
| placebo（等量中性文本） | **73.8%** |
| treatment（真技能） | **71.3%** |

```
uplift          −2.5pp
headroom        −10%（负的：treatment 低于 placebo）
95% CI          [−7.9, +2.5]   → 跨 0，不显著
placebo_effect  +0.0pp
N               48（A 级）
```

**结论（严格版）**：在这个任务集、这个模型、这个 harness 上，
`modern-web-guidance` 的净增益是 **−2.5pp，95%CI 跨 0**，测不出正增益，也测不出确定的负增益。

**要特别说清楚**：这**不能**用来反驳 MWG 自己公开的 +27~36pp。
他们测的是自己的 harness、自己的任务、自己的评分流程；我们测的是
「把它当技能包投进一个通用 agent loop，在 48 个自己造的小任务上」。
两者不是一个实验。

## 三、为什么必须做亚组分析

48 题里有 28 题 baseline 就是 100%，**天花板顶死，技能再强也没有空间可填**。

| 组 | 题数 | baseline | placebo | treatment | 三臂 uplift |
|---|---|---|---|---|---|
| 全集（ITT，主结论） | 48 | 73.8% | 73.8% | 71.3% | **−2.5pp** |
| 天花板组（baseline=100%） | 28 | 100% | 96.4% | 94.3% | −2.1pp |
| 有空间组（baseline<100%） | 20 | 37.0% | 42.0% | 39.0% | −3.0pp |

**两组都是负的。** 这不是「天花板压低了大盘」，天花板组和有空间组都一样没吃到增益。

**声明**：这是**事后**亚组分析，只作探索性证据；主结论仍是全集 ITT。

## 四、本轮最刺眼的数字：激活率 23%

treatment 臂 239 次运行里，只有 **69 次**真的调用了 `activate_skill`（placebo 臂 42 次）。

而这个技能的 description 原文写着：

> MANDATORY: Execute FIRST for all HTML/CSS and clientside JS tasks. Do NOT skip — web APIs evolve rapidly and training weights contain obsolete patterns.

**写了 MANDATORY，模型仍然只有 23% 的时候会去用。**

于是 treatment 臂实际上是「77% 的 run 等于 baseline + 23% 的 run 做了点别的」的混合体，
这就是为什么三臂数字如此接近，**你测到的主要是「模型愿不愿意用技能」，而不是「技能内容有没有用」**。

### per-protocol：激活之后反而更差

| treatment 臂内部 | 通过率 | n |
|---|---|---|
| 激活过的 run | **61.4%** | 70 |
| 没激活的 run | **75.3%** | 170 |

差 **−13.9pp**。但**这不能当因果读**：模型是在「觉得难/不确定」时才去求助的，
难任务本来就更容易失败（自我选择偏差）。

要分清「内容有害」还是「求助流程有害」，只能强行让每次运行都加载技能，见下一节。

## 五、forced activation 对照（技能内容本身的效果）

`--activation forced` 把技能正文**直接注入系统提示**，不走模型自主选择、也不需要 agent 去跑 `npx`。
三臂仍然对称：treatment 注入 9.8k token 的真技能，placebo 注入 9.8k token 的等量中性文本。
48 题 × 3 臂 × 3 重复 = 432 run，激活率 **100%**（这是设计使然）。

| 组 | 题数 | baseline | placebo | treatment | 三臂 uplift | 安慰剂效应 |
|---|---|---|---|---|---|---|
| **forced 全集** | 48 | 71.5% | 63.9% | 69.4% | **+5.6pp** | **−7.6pp** |
| 天花板组（baseline=100%） | 31 | 100% | 88.2% | 89.2% | +1.1pp | −11.8pp |
| 有空间组（baseline<100%） | 17 | 19.6% | 19.6% | 33.3% | **+13.7pp** | 0.0pp |

95%CI（三臂）：**[−2.8, +13.2]** → 跨 0，不显著。

### 这张表最值得看的是 placebo 那一列

**往上下文里灌 9.8k token 的中性文本，通过率掉了 7.6pp。**
换成真技能正文，只掉 2.1pp，于是 `uplift` 变成正的：

```
uplift = treatment − placebo = +5.6pp      ← 技能内容本身值这么多
但   treatment − baseline  = −2.1pp       ← 装上它整体仍略低于不装
两臂口径会看到                −2.1pp       ← 「别装，掉分」
```

三个数字都对，但只有三臂口径告诉你**为什么**：
技能内容是有价值的（+5.6pp），只是它**抵不平自己带来的上下文成本**（−7.6pp 里的那一部分）。

### 有空间的那 17 题里，效应大三倍

| 组 | uplift |
|---|---|
| 天花板组（31 题，baseline 100%） | +1.1pp |
| 有空间组（17 题，baseline 19.6%） | **+13.7pp** |

**同样的技能，在「本来就不会做」的任务上是 +13.7pp，在「本来就会做」的任务上几乎是 0。**
这就是 `docs/09` 里 uplift modeling 那句「*persuadables*」的实测版本：
**技能不是让所有任务变好，它是让本来做不出的那部分变好。**

（声明：亚组按 baseline 事后切开，只作探索性证据。）

### 与 auto 模式的对照

| 模式 | 激活率 | baseline | placebo | treatment | uplift | 95%CI |
|---|---|---|---|---|---|---|
| `auto`（模型自己决定） | 23% | 73.8% | 73.8% | 71.3% | −2.5pp | [−7.9, +2.5] |
| `forced`（注入正文） | 100% | 71.5% | 63.9% | 69.4% | +5.6pp | [−2.8, +13.2] |

**同一个技能包，两种激活策略给出不同符号。** 两个都成立，因为它们问的不是一件事：

- `auto` 回答「**把它丢给一个会自己拿主意的 agent，它有用吗**」，接近没有，因为 77% 的运行根本没激活它；
- `forced` 回答「**如果它真的被加载进上下文，它的内容值多少分**」，+5.6pp，但抵不平自身成本。

**结论：一个技能包的效果，取决于「激活率 × 内容质量」，而这两项必须分开测。**
这也是这一轮给协议提的修改建议：`--activation` 应当成为必须声明的测量条件（见 §八 P0）。

## 六、安慰剂效应不是常数，而且 auto 模式下它根本估不准

三轮数据放一起（激活率来自 `tier1.activation.by_arm`）：

| 轮次 | 技能包 | 模式 | treatment 激活率 | placebo 激活率 | 实际注入量 | placebo_effect | uplift |
|---|---|---|---|---|---|---|---|
| 第一轮 | `agent-skills`（25 技能） | auto | 34.4% | **0.0%** | treatment 端 4k 级、placebo 端 **0** | **−4.4pp** | +2.2pp |
| 第二轮 | `modern-web-guidance`（1 技能） | auto | 29.2% | 17.5% | 两端都是 9.8k 量级，但只在被激活的 run 里 | **0.0pp** | −2.5pp |
| 第二轮 | `modern-web-guidance`（1 技能） | forced | 100% | 100% | **100% 的 run 注入 9.8k** | **−7.6pp** | +5.6pp |

**第一轮那行直接推翻了本文档早先的说法。** 之前写的是「安慰剂臂时不时激活到一份 4k 级中性文档，
所以有 −4.4pp」，查了 `by_arm` 才发现**第一轮 placebo 臂的激活率是 0.0%，一次都没激活**。
一行中性文本都没进上下文，照样掉 4.4pp。那就是噪声（`docs/14` 当时也算过：约 1 个标准误量级）。

所以正确的说法是三层：

1. **唯一能归因的安慰剂效应是 forced 那行**：100% 的 run 都注入 9.8k 中性文本，通过率掉 7.6pp。
   这是「上下文变长本身值多少分」的可测版本。
2. **auto 的两行不能用来论证「注入越多、安慰剂效应越大」**：placebo 激活率从 0% 到 17.5%，
   `placebo_effect` 在 −4.4pp 与 0.0pp 之间抖，量级都在噪声里（n=30 / n=48 题）。
3. **因此 auto 模式下的安慰剂效应是不可估的**，它既可能是 0，也可能是 −7pp，
   取决于模型这一轮心情好不好、愿不愿意去点那个技能。你没法把它从 uplift 里减干净。

所以 §八 的 P0 建议是把注入量变成实验条件，而不是「把安慰剂做大一点」：
`--activation forced` + `--preload-budget` 让安慰剂效应从「碰巧」变成「设计」。

顺带一个副产品：**安慰剂臂是可以被激活的，而且真的会被激活**（第二轮 17.5%）。
说明「要不要加载一段上下文」这个决策两臂都经历了，激活本身不是 treatment 独有的。
但 description 写得诱人的那边更容易被点开，两臂激活率并不相等（29.2% vs 17.5%），
下一轮把 placebo 的 description 也写成等长祈使句，让点击率对齐（见 §九 9.2）。

## 七、这一轮证明了什么、没证明什么

**证明了**

1. 48 题 × 5 重复 × 3 臂的管线能跑完（720 run，0 次人工干预，$60.93）；forced 再跑 432 run（$71.69）。
2. 技能激活率是**可测的**，而且远低于技能作者的心理预期：写了 `MANDATORY` 也只有 **23%**。
3. 安慰剂效应**只有在注入量可控时才估得出来**（forced：−7.6pp）；auto 下注入与否由模型决定，
   安慰剂效应在噪声里（−4.4pp ~ 0.0pp），不可估也不可减。
4. 同一技能在 auto 与 forced 下可以给出**不同符号**的 uplift（−2.5pp vs +5.6pp）。
5. 一个公开宣称 +27~36pp 的技能包，在另一套任务与 harness 上可以是 −2.5pp（auto）。
6. 安慰剂臂**也会**被模型激活（17.5%），激活不是 treatment 独有的，但两臂激活率不相等，
   这是下一轮要修的不对称（§九 9.2）。

**没证明**

1. 「MWG 没用」，一个任务集、一个模型、一个 harness，不够。而且 forced 下它是 +5.6pp。
2. 「技能都会掉分」，第一轮的 25 技能包 auto 下是 +2.2pp。
3. 「+13.7pp 的亚组结论可推广」，事后切分、17 题、CI 宽。

## 八、下一轮该做什么

| 优先级 | 改动 | 为什么 |
|---|---|---|
| P0 | 把 `--activation auto\|forced` 写进协议，作为**必须声明**的测量条件 | 同一技能两种模式符号相反，不声明就无法比较 |
| P0 | 任务集继续加难度：让 baseline 落到 30–60% | 现在 31/48 题天花板 100%，一半测量范围被吃掉 |
| P1 | 安慰剂按「每次运行注入量」匹配（而非整包总量） | auto 下注入量不确定就估不出安慰剂效应；forced 才给出 −7.6pp |
| P1 | placebo 的 description 写成与真技能等长的祈使句 | 本轮两臂激活率 29.2% vs 17.5%，不对称 |
| P1 | 加 `--preload-budget` 敏感性分析（4k / 8k / 12k） | 注入多少正文会改变结论方向 |
| P2 | 跨 harness 测同一技能的激活率 | 激活率是技能可用性的第一道门槛 |

## 九、这一轮之后改掉的东西（工程侧）

### 9.1 激活率进卡片、进榜单

之前 `uplift` 数字只带 `N` 和 `CI`，读者看不出 `treatment` 臂里有多少 run 其实还是 `baseline`。
现在卡片带 `tier1.activation`：

```
Tier 1   uplift −2.5pp / headroom −9.5%   95%CI [−7.9, 2.5] · N=48 · placebo +0pp
激活      自动激活 23%（treatment 29% / placebo 18%）
         ⚠️ 大半 run 没触发技能，这个 uplift 主要反映「肯不肯调工具」
```

榜单页（`uplift site`）按 `任务集 · 等级 · 激活条件` 分表，同一个技能包的 auto 与 forced
各占一张表，**不许只挂好看的那个**。表里也多了「激活率」列。

### 9.2 一个之前没人注意的数：安慰剂臂也被激活了 18%

`activate_skill` 是模型自主调的，而 placebo 臂的「技能」是中性文本包成同名结构，
模型照样会去调它。所以两臂都有激活，只是比例不同：

| 臂 | 激活率（auto） | 说明 |
|---|---|---|
| treatment | 29.2% | 真技能，description 写得像「MANDATORY」 |
| placebo | 17.5% | 中性文本，description 无信息量 |
| 合计（剔除 baseline） | **23.3%** | 对外报的就是这个数 |

这对安慰剂设计的含义是**好消息**：两臂都经历了「要不要加载一段上下文」的同一个决策过程，
激活本身不是 treatment 独有的。但它同时暴露一个小的不对称，**描述写得诱人的那边更容易被点开**，
于是 treatment 臂平均注入的 token 比 placebo 臂多一点。这个偏差在三臂设计里并不消失，
只是被「安慰剂也要有同样的诱人外壳」这条要求部分抵消。下一轮可以做得更彻底：
**placebo 的 description 用与真技能等长、同样祈使语气的句子**，让点击率对齐。

### 9.3 出卡工具

`tools/make-cards.ts` 现在支持：

- `--runs-db=a.db,b.db,…`：同一个包的 Tier 1 取第一份命中的库（第二轮有 ITT / forced 两份）；
- `--only=id,id`：只重出某几个包（换一种条件出卡时不必把 5 个包的探针全跑一遍）；
- `--suffix=forced`：输出 `results/<id>.forced.json|.md|.badge.svg`，与默认条件互不覆盖。

`protocol_notes` 里会写明 `activation=auto|forced` 与实际来源库，卡片自带出处。
