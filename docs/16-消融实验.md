# 16 · 消融实验：提示词里给不给 API 名，差 100pp

> 这一轮的目标只有一个：搞清楚**为什么 48 题里有 28 题 baseline 就是 100%**，以及能不能把它降下来。
> 结论先说：能，但只有一种降法是对的；而且我们在这个过程中发现了两处评分器把"正确做法"判成错。
> 所有数字都是小样本（n=3 或 n=5），只作方向，不作出结论——本文档最后有一节专门讲它证明不了什么。

---

## 一、假设

v1.1 的题大部分长这样（`wmg-044`）：

> reorder.js 通过 removeChild + insertBefore 移动节点……改成新 API：
> **用 element.moveBefore(node, ref)** 保留节点状态，不要再 removeChild。

API 名字、调用形状、甚至连"用哪个方法"都写进去了。这不是任务，这是**转写**。
基线模型只要会打字就能 100%，技能没有信息差可补，uplift 必然趋近 0。

于是假设是：

> 把提示词里的 API 名删掉，只留"要解决什么"，同一道题就从「照抄」变成「你知道平台有这个能力吗」。
> 技能要补的正是这个信息差。

---

## 二、设计：消融对（ablation pair）

| 组 | 题号 | fixture / 评分器 | 提示词 |
|---|---|---|---|
| popover 给名 | `wmg-045` | 同一份 | 明写 `popover` / `popovertarget` / `showPopover()` |
| popover 不给名 | `wmg-057` | **同一份** | 只说「改成浏览器原生的浮层机制，触发按钮与面板用原生属性关联」 |
| moveBefore 给名 | `wmg-044` | 同一份 | 明写 `element.moveBefore(node, ref)` |
| moveBefore 不给名 | `wmg-058` | **同一份** | 只说「改成原生移动能力，节点不算被重新插入」 |

两条硬约束保证"只改了一个变量"：

1. fixture 逐字节相同（`tests/taskset.test.ts` 里有一条断言在守这件事：`wmg-058` 的 `reorder.js` 必须 `wmg-044` 的完全相同）；
2. 评分器文件相同（同一套 `rules.json`）。

运行条件：`--activation forced`（保证技能正文真的进了上下文，否则 auto 模式只有 23% 的激活率，信号被湮没），
3 臂 × 3 repeats。技能包是 `GoogleChrome/modern-web-guidance-src` 的 `guides/`，
注入量中位数 **2,441 tok**（treatment 与 placebo 等量）。

---

## 三、结果

三臂通过率（`--repeats 5`，n=5/格，2026-11-13 重测；60 次 run，$12.20）：

| 题号 | 提示词 | baseline | placebo | treatment | uplift (t−p) |
|---|---|---|---|---|---|
| `wmg-044` | 给名 `moveBefore` | 60% (3/5) | 40% (2/5) | **0%** (0/5) | −40pp |
| `wmg-058` | 不给名 | **0%** (0/5) | 0% (0/5) | **40%** (2/5) | **+40pp** |
| `wmg-045` | 给名 `popover` | 60% (3/5) | 80% (4/5) | 60% (3/5) | −20pp |
| `wmg-057` | 不给名 | 60% (3/5) | 100% (5/5) | 40% (2/5) | −60pp |

**先把不稳定说清楚。** 同一套 fixture、同一个模型，n=3 那一轮是
`044: 100/67/0`、`058: 0/0/67`、`057: 100/100/100`；n=5 这一轮是上表。
差别最大的 `057` 从 100% 掉到 40–60%。**这种抖动本身就是结论的一部分**：
每格只有 3–5 次，任何单点差值的 CI 都宽到能跨 0，下面所有话都只能当方向。

> `wmg-057` 的 40%（n=3 那轮是 100%）与评分器无关——规则已经修成 `popover` + `(popovertarget|showPopover)`，
> 40% 指的是这些 run 里模型**根本没用 popover**，退回了手写 class 开关。
> 注入了技能反而更容易不用原生 API，这个方向值得单独查（见 §六.4）。

把两轮放在一起看，稳定成立的是两组对比：

```
给名 moveBefore  → baseline 60~100%，treatment 0%          （技能让它写回退，被判犯规）
不给名 moveBefore → baseline 0%，      treatment 40~67%    （技能补上了它不知道的 API）
```

`058` 是四格里唯一「baseline 0% 而 treatment 明显抬头」的，也是唯一一格技能真的在补信息差。

## 四、三个发现

### 4.1 给 API 名的题就是转写题：同一份代码，0% 对 100%

`044` 与 `058` 的 fixture、评分器、臂、重复次数完全一样，只有 `prompt.md` 不同：

```
044  提示词写 moveBefore        → baseline 100%
058  提示词只说"移动但不重新插入" → baseline   0%
```

**100 个百分点的差距，来自提示词里那一个词。** 这说明 v1.1 里那 28 道 100% 的题，
测的是"会不会照抄"，不是"知不知道"。

### 4.2 但"不给名"只在技能真覆盖这个 API 时才有意义

| API | `guides/` 里出现次数 | 给名 baseline | 不给名 baseline | 不给名 treatment |
|---|---|---|---|---|
| `popover` | 436 | 67% | **100%** | 100% |
| `moveBefore` | 39 | 100% | **0%** | **67%** |

- `popover` 太常见，模型自己就会，不给名也 100% → 天花板不是提示词造成的，是**模型先验太强**。
- `moveBefore` 冷门，模型先验没有，不给名就 0%……**而技能里有（39 处）**，于是 treatment 拉到 67%。

我还顺带做了一组对照：另外写了 8 道"现代 JS"题（`structuredClone` / `Intl.Segmenter` /
`Set.prototype.union` / `URL.parse` …），给名时 baseline 100%，不给名时 baseline 0%——
**而这两个 API 在 `guides/` 里出现 0 次，所以 treatment 也是 0%。**

这三个点连起来是一条判据，下一轮选题就靠它：

```
uplift 可能出现  ⟺  任务要求的内容  ∩  技能真的写了的内容  ∩  模型先验里没有的内容
```

三者缺任何一个，uplift 必然是 0——第 1 项缺了是题太简单，第 2 项缺了是技能没覆盖，
第 3 项缺了是模型已经会了。**v1.1 的 28 道天花板题，基本都缺第 1 项和第 3 项。**

### 4.3 评分器会把"技能教的正确做法"判成错——一共五次

这一节是本文档最该被记住的部分。五次误判，同一个根因，方向各不相同。

**第一次（`wmg-057` 第一版规则）**：要求 `showPopover\(\)`。
模型用了声明式 `popover` 属性 + `popovertarget` 按钮，脚本里一行 JS 都不需要——这是**更现代**的答案。
评分器判 0，连续 6 次。改成 `popovertarget|showPopover\(\)` 之后：

```
修规则前：baseline 0% / placebo 33% / treatment 0%
修规则后：baseline 100% / placebo 100% / treatment 100%
```

**第二次（`wmg-057` 第二版规则，方向相反）**：只认 `popovertarget`。
模型这次全用了 `popover` + `showPopover()` 命令式写法 → 又判 0（`缺少：popovertarget`）。
最终规则：`popover` + `(popovertarget|showPopover\(\))`。

**第三次（`wmg-044` treatment 臂）**：要求"不要再 removeChild"，同时 forbid `insertBefore\(`。
模型读了 guide，按 guide 的建议写了**特性检测 + 回退**：

```
parent.moveBefore(node, ref)                      ← 首选，保留状态
if (!('moveBefore' in Element.prototype)) {        ← 按 guide 要求做渐进增强
  parent.removeChild(node); parent.insertBefore(node, ref);
}
```

三臂里 treatment 是唯一读到 guide 的臂，也是唯一写回退的臂 → **唯一被判 0 的臂**。
换句话说：**它因为听了技能的话而被扣分。**（n=5 那一轮依然是 0/5 对 baseline 3/5。）

**第四次（`wmg-061`）**：规则写 `@container\s+scroll-state\(`——只匹配**不具名**容器查询。
模型写的是 `@container sticky-header scroll-state(stuck: top)`（具名，更常见）。
判 0 三次。改成正则里允许可选容器名之后，treatment 从 0/3 变 3/3。

**第五次（`wmg-064`）**：规则要求 `position-anchor:`。
模型用了 `anchor-name:` + **`position-area: top center`**——同一套锚点定位 API 里更省事的那个。判 0 两次。改成 `anchor-name:` + `(position-anchor:|position-area:|anchor=)` 后恢复。

同一个根因，一句话：**正则评分器只认得出"我预期的那一种写法"，而正确答案有等价类。**


**正面解法**：给 `wmg-058` 换掉正则、上行为测试。
做法是造一个够用的假 DOM（`moveBefore` / `removeChild` / `insertBefore` 各自记调用次数），
然后断言两件事：**顺序对**，且**首选走的是 `moveBefore`**（`removeChild`/`insertBefore` 调用数为 0）。

```js
// 规则从
forbid: ['removeChild\\(', 'insertBefore\\(']     // ← 把回退分支也一起判死
// 改成
forbid: [],  require: ['moveBefore\\(']            // ← 只要求"用到了"，偏好由行为测试判
```

参考解故意写成**带回退**的版本（首选 `moveBefore`，不支持时才 `removeChild` + `insertBefore`），
`tests/graders-behavioral.test.ts` 里它必须判过。这一改让「渐进增强」从犯规变成正解，
而且没法被"往注释里抄一句 moveBefore"骗过去——那玩意儿的调用次数是 0。

### 4.4 这条根因带来的一个副产品：treatment 的效应被系统性低估

`wmg-044` 在 forced 模式下 treatment = 0%、baseline = 100%。如果不看 §4.3，
这张表会得出"技能让人变差 100pp"的结论——而真相是"技能让人加了一段回退分支"。

按同样逻辑回看第二轮那 720 次 run：凡是 guide 建议"加特性检测/回退"的地方，
treatment 臂都会多写一份旧代码，而我们的 forbid 规则会把它判成犯规。
**所以 `docs/15` 里那个 +5.6pp 是低估，不是高估。**（低估多少，要等行为型评分器上来才知道。）

## 五、这一轮实际改了哪些评分器

| 题号 | 改动 | 原因 |
|---|---|---|
| `wmg-057` | 删掉 `showPopover\(\)` 强制项 | 声明式 `popovertarget` 是等价正解 |
| `wmg-057` | 再加 `(popovertarget\|showPopover\(\))` alternation | 命令式 `showPopover()` 同样是等价正解 |
| `wmg-049`~`056` | 新增**行为测试**（把代码 import 进来跑） | 正则能被"把 API 名抄进注释"骗过，行为不能 |
| `wmg-061` | `@container\s+scroll-state\(` → 允许可选容器名 | 具名容器查询（`@container foo scroll-state(...)`）是等价正解 |
| `wmg-064` | `position-anchor:` → `(position-anchor:\|position-area:\|anchor=)` | 选中锚点有三种等价写法 |
| `wmg-058` | 去掉 forbid，改行为测试 | 「首选 + 回退」是正确工程，正则分不出来 |

`wmg-044` / `wmg-045` 保持不动：它们是 720 次 run 那批数据的一部分，改了就前后不可比。
它们的问题记在 §六。

## 六、还欠着的（下一轮必须做）

1. **`044` 的"首选 + 回退"问题还没解决。** `058` 已经用假 DOM 的行为测试解决了
   （见 §4.3 的"正面解法"），但 `044` 是 720 次 run 那批数据的一部分，改了就前后不可比，
   所以它仍旧用会误判回退的旧规则。**读者看到 `044` 的 treatment=0% 时务必记得这条。**
2. **n 太小。** 每格 3 次，95%CI 能把 0% 和 67% 连起来。上面所有数字都只能当方向。
3. **`popover` 那条已经证明：模型先验太强的 API 出不了题。** 下一轮选题前先做个
   「先验探测」：同一个 fixture 用非技能模型跑 3 次，baseline > 80% 的题直接不进池子。
4. **行为测试的运行时依赖**：`URL.parse` 这类新 API 在老 Node 上不存在，
   会让整题对所有解都判 0。`tests/graders-behavioral.test.ts` 就是防这个的——它一旦红，
   说明运行时不支持参考解，而不是模型不会。

## 七、下一轮选题判据（可以直接照做）

```
1. 从技能包里 grep 候选 API，只留出现 ≥5 次的（技能真的覆盖）
2. 出题：提示词只写"症状 / 要求"，不写 API 名、不写调用形状
3. 评分器：行为测试为主（import 候选代码跑边界用例），正则只做 forbid 兜底
4. 先验探测：非技能模型 ×3，baseline > 80% 的题退回重写
5. 消融对：每题必须有一个"给名"的孪生题，用来验证"不给名"确实更贵
6. **规则定稿前必须跑一遍 baseline，把模型实际写出的等价形式收齐**，
   再写 require 的 alternation。本文档记录的五次误判，全都是跳过这一步造成的
```

第 6 条是追加实验加进去的，也是最便宜的一条：**一轮 baseline 只要几美元，
一次误判会让整批结论反过来。**

第 5 条是这一轮最大的方法论收获：**没有孪生题的难度是没法归因的**——
你不知道 baseline 低是因为"模型不知道"，还是因为"提示词写歪了"。

## 八、追加实验：照 §七 的判据做了 6 道题（`wmg-059~064`）

选题严格按 §七 第 1 条：先在 `guides/` 里 grep，只留技能覆盖得到的平台新特性，
提示词一律只写症状。命中次数（括号内）与结果：

| 题号 | 特征 | 技能覆盖 | baseline | placebo | treatment | uplift |
|---|---|---|---|---|---|---|
| `wmg-060` | `appearance: base-select` | 38 处 | **0%** (0/3) | 0% (0/3) | **100%** (3/3) | **+100pp** |
| `wmg-061` | `container-type: scroll-state` | 74 处 | 67% (2/3) | 67% (2/3) | **100%** (3/3) | **+33pp** |
| `wmg-064` | `anchor-name` / 锚点定位 | 21 处 | 67% (2/3) | 67% (2/3) | 67% (2/3) | 0pp |
| `wmg-059` | `field-sizing: content` | 24 处 | 100% (3/3) | — | — | 天花板 |
| `wmg-062` | `subgrid` | 29 处 | 100% (3/3) | — | — | 天花板 |
| `wmg-063` | `light-dark()` | 51 处 | 100% (3/3) | — | — | 天花板 |

三题有空间的合计（每格 n=9）：baseline **44%** → treatment **89%**，uplift **+45pp**。

### 8.1 `wmg-060` 是这个项目目前最干净的一个正结果

```
baseline 0/3    placebo 0/3    treatment 3/3
```

- baseline 0：模型**从不**自发用 `appearance: base-select`；
- placebo 0：注入 2,441 tok 中性文本不能把它变会；
- treatment 3/3：注入技能正文就会了。

三重条件同时成立，才能说"这 3 次通过是技能带来的"。这也是第一次在
**提示词不给答案**的条件下拿到满格 uplift（+100pp）。

### 8.2 另外 3 题为什么还是天花板

`field-sizing` / `subgrid` / `light-dark()` 都不给名字，模型照样 100%。
它们和 §4.2 里的 `popover` 是同一类：**技能写得再好，也补不了"模型已经会"的差值。**
这三次失败和选题判据无关（三项条件里第 3 项"模型先验缺失"没成立），
但值得记下来：**CSS 基础特性的先验普遍比 JS 新 API 强**。

### 8.3 但这两题第一次测出来是反的

`061` 和 `064` 第一版结果分别是 `67/67/0`（−67pp）和 `0/67/33`（−33pp），
看着像"技能让模型变差"。查下去发现又是评分器的等价类问题（§4.3 第四次、第五次）。
修完规则重测：`67/67/100` 与 `67/67/67`。**两次"技能有害"的结论，一次也没站住。**

### 8.4 仍然不稳定的地方

`wmg-064` 的 baseline 在两批 run 里分别是 **0/3** 和 **2/3**。同一道题、同一个模型、
同一份提示词，n=3 就差 67 个百分点。这不是评分器的问题，是模型本身的抖动。
**任何 n=3 的单题结论都不该被写进对外材料**——这也包括本文档里所有单题数字。
