# 16 · 消融实验：提示词里给不给 API 名，差 100pp

> 目标只有一个：搞清楚 48 题里有 28 题 baseline 就是 100% 的原因，以及能不能把它降下来。
> 结论是能，但只有一种降法是对的；过程中还发现五处评分器把正确做法判成了错。
>
> 这里的数字都是小样本（n=3、5、10），只作方向，不作出结论。最后有一节专门讲它证明不了什么。

## 一、假设

v1.1 的题大部分长这样（`wmg-044`）：

> reorder.js 通过 removeChild + insertBefore 移动节点……改成新 API：用 element.moveBefore(node, ref)
> 保留节点状态，不要再 removeChild。

API 名字、调用形状、用哪个方法都写进去了。这不是任务，是转写。基线模型会打字就能 100%，
技能没有信息差可补，uplift 必然趋近 0。

假设：把提示词里的 API 名删掉，只留「要解决什么」，同一道题就从照抄变成「你知道平台有这个能力吗」。
技能要补的正是这个信息差。

## 二、设计

| 组 | 题号 | fixture / 评分器 | 提示词 |
|---|---|---|---|
| popover 给名 | `wmg-045` | 同一份 | 明写 `popover` / `popovertarget` / `showPopover()` |
| popover 不给名 | `wmg-057` | 同一份 | 只说「改成浏览器原生的浮层机制，触发按钮与面板用原生属性关联」 |
| moveBefore 给名 | `wmg-044` | 同一份 | 明写 `element.moveBefore(node, ref)` |
| moveBefore 不给名 | `wmg-058` | 同一份 | 只说「改成原生移动能力，节点不算被重新插入」 |

两条约束保证只改了一个变量：fixture 逐字节相同（`tests/taskset.test.ts` 里有一条断言在守，
`wmg-058` 的 `reorder.js` 必须等于 `wmg-044` 的），评分器文件相同（同一套 `rules.json`）。

运行条件：`--activation forced`，保证技能正文真的进了上下文，否则 auto 模式只有 23% 的激活率，
信号被湮没。3 臂 × 3 repeats。技能包是 `GoogleChrome/modern-web-guidance-src` 的 `guides/`，
注入量中位数 2,441 tok，treatment 与 placebo 等量。

## 三、结果

三轮跑过同一批题，每轮 n 不同。放在一起看，抖动本身就是结论的一部分。

| 题号 | 提示词 | n=3（先把这三个数当方向） | n=5 | n=10（定稿） |
|---|---|---|---|---|
| `wmg-044` | 给名 | 100 / 67 / 0 | 60 / 40 / 0 | 60 / 60 / **80** |
| `wmg-058` | 不给名 | 0 / 0 / 67 | 0 / 0 / 40 | 10 / 0 / **40** |
| `wmg-045` | 给名 | 67 / 67 / 67 | 60 / 80 / 60 | 未重跑 |
| `wmg-057` | 不给名 | 100 / 100 / 100 | 60 / 100 / 40 | 未重跑 |

（每格是 baseline / placebo / treatment 的通过率百分比。）

n=10 那一轮共 150 次 run，$29.79，五题合计：

| 题号 | baseline | placebo | treatment | uplift |
|---|---|---|---|---|
| `wmg-044` | 6/10 | 6/10 | 8/10 | +20pp |
| `wmg-058` | 1/10 | 0/10 | 4/10 | +40pp |
| `wmg-060` | 0/10 | 0/10 | 6/10 | +60pp |
| `wmg-061` | 6/10 | 7/10 | 9/10 | +20pp |
| `wmg-064` | 4/10 | 3/10 | 7/10 | +40pp |
| 合计 | 34% | 32% | 68% | +36pp，CI [+24, +48] |

安慰剂效应 −2pp。同样注入 2,441 tok，中性文本不值钱，真技能值 36 个点。

这一轮同时推翻了上一轮三个负结论：`044` 的 −40pp、`061` 的 −67pp、`064` 的 −33pp，
全部来自评分器误判加小样本抖动。`044` 换成行为评分后从 0/5 变 8/10，那个 −40pp 是仪器的产物。

## 四、三个发现

### 4.1 给 API 名的题就是转写题

`044` 与 `058` 的 fixture、评分器、臂、重复次数完全一样，只有 `prompt.md` 不同：

```
044  提示词写 moveBefore          → baseline 100%
058  提示词只说"移动但不重新插入"   → baseline   0%
```

100 个百分点的差距，来自提示词里那一个词。v1.1 那 28 道 100% 的题，测的是会不会照抄。

### 4.2 不给名只在技能真覆盖这个 API 时才有意义

| API | `guides/` 里出现次数 | 给名 baseline | 不给名 baseline | 不给名 treatment |
|---|---|---|---|---|
| `popover` | 436 | 67% | 100% | 100% |
| `moveBefore` | 39 | 100% | 0% | 67% |

`popover` 太常见，模型自己就会，不给名也 100%，天花板不是提示词造成的，是模型先验太强。
`moveBefore` 冷门，模型先验没有，不给名就 0%，而技能里有（39 处），于是 treatment 拉到 67%。

顺带做过一组对照：另外写了 8 道现代 JS 题（`structuredClone`、`Intl.Segmenter`、`Set.prototype.union`、
`URL.parse` 等），给名时 baseline 100%，不给名时 baseline 0%，而这两个 API 在 `guides/` 里出现 0 次，
所以 treatment 也是 0%。三个点连起来是一条判据：

```
uplift 可能出现  ⟺  任务要求的内容  ∩  技能真的写了的内容  ∩  模型先验里没有的内容
```

三者缺一，uplift 必然是 0。第 1 项缺了是题太简单，第 2 项缺了是技能没覆盖，第 3 项缺了是模型已经会了。
v1.1 那 28 道天花板题，基本都缺第 1 项和第 3 项。

### 4.3 评分器把正确做法判成错，五次

这一节是该被记住的部分。五次误判，同一个根因，方向各不相同。

1. `wmg-057` 第一版要求 `showPopover\(\)`。模型用声明式 `popover` 属性加 `popovertarget` 按钮，
   脚本里一行 JS 都不需要，这是更现代的答案。评分器判 0，连续 6 次。改成
   `popovertarget|showPopover\(\)` 之后，baseline 从 0% 变 100%。
2. `wmg-057` 第二版只认 `popovertarget`。模型这次全用命令式 `showPopover()`，又判 0。
   最终规则写成 `popover` 加 `(popovertarget|showPopover\(\))`。
3. `wmg-044` 的 treatment 臂。要求「不要再 removeChild」，同时 forbid `insertBefore\(`。
   模型读了 guide，按 guide 的建议写了特性检测加回退：`moveBefore` 首选，不支持时才
   `removeChild` 加 `insertBefore`。三臂里 treatment 是唯一读到 guide 的臂，也是唯一写回退的臂，
   于是成了唯一被判 0 的臂。它因为听了技能的话而被扣分。
4. `wmg-061` 规则写 `@container\s+scroll-state\(`，只匹配不具名容器查询。模型写的是
   `@container sticky-header scroll-state(stuck: top)`，具名，更常见。判 0 三次。允许可选容器名之后，
   treatment 从 0/3 变 3/3。
5. `wmg-064` 规则要求 `position-anchor:`。模型用 `anchor-name:` 加 `position-area: top center`，
   同一套锚点定位 API 里更省事的那个。判 0 两次。改成三种等价写法都收之后恢复。

同一个根因：正则评分器只认得出我预期的那一种写法，而正确答案有等价类。

正面解法落在 `wmg-058` 上。造一个够用的假 DOM，`moveBefore`、`removeChild`、`insertBefore`
各自记调用次数，断言顺序对且首选走 `moveBefore`：

```js
// 规则从
forbid: ['removeChild\\(', 'insertBefore\\(']     // 把回退分支也一起判死
// 改成
forbid: [],  require: ['moveBefore\\(']            // 只要求"用到了"，偏好由行为测试判
```

参考解故意写成带回退的版本，`tests/graders-behavioral.test.ts` 里它必须判过。这样一来「渐进增强」
从犯规变成正解，而且没法靠往注释里抄一句 `moveBefore` 蒙过去，那东西的调用次数是 0。

## 五、treatment 的效应被系统性低估

`044` 在 forced 模式下 treatment 曾跑出 0%、baseline 100%。不看第四节的话，这张表会得出
「技能让人变差 100pp」，而真相是技能让人加了一段回退分支。

同一逻辑回看第二轮那 720 次 run：凡是 guide 建议加特性检测或回退的地方，treatment 臂都会多写一份旧代码，
而 forbid 规则会把它判成犯规。所以 `docs/15` 里那个 +5.6pp 是低估，不是高估。低估多少，要等行为型评分器铺开才知道。

## 六、还欠着的

`wmg-044` 现在也换成了行为评分，与 `058` 同一套假 DOM。代价写清楚了：1.1.0 时代 `044` 的数字来自旧规则，
与 1.4.x 不可直接比较，引用时要注明评分器版本。

`044` 与 `058` 之间还差一个变量没控住：`044` 的提示词说「不要再 removeChild」，`058` 说「不算被重新插入」。
前者是禁令，后者是描述，语气不同。要彻底干净，得把两句改成同一种句式。

`n=10` 也只有 5 个配对点，CI 宽到 ±12pp，而且只有一个技能包、一个模型、一个 harness。

行为测试依赖运行时。`URL.parse` 这类新 API 在老 Node 上不存在，会让整题对所有解都判 0。
`tests/graders-behavioral.test.ts` 就是防这个的，它一旦红，说明运行时不支持参考解，而不是模型不会。

## 七、下一轮选题判据

```
1. 从技能包里 grep 候选 API，只留出现 ≥5 次的（技能真的覆盖）
2. 出题：提示词只写症状，不写 API 名、不写调用形状
3. 评分器：行为测试为主（import 候选代码跑边界用例），正则只做 forbid 兜底
4. 先验探测：非技能模型 ×3，baseline > 80% 的题退回重写
5. 消融对：每题配一个「给名」的孪生题，用来验证「不给名」确实更贵
6. 规则定稿前先跑一遍 baseline，把模型实际写出的等价形式收齐，再写 require 的 alternation
```

第 5 条是这一轮最大的收获。没有孪生题的难度是没法归因的，你不知道 baseline 低是因为模型不知道，
还是因为提示词写歪了。第 6 条最便宜：一轮 baseline 几美元，一次误判会让整批结论反过来。
