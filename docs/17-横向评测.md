# 17 · 横向评测：12 个技能包的写法差异

> 这一篇不测内容对不对，只测写法与成本。这两件事不需要模型就能看清楚，而且它们决定一个技能包
> 有没有机会起作用。榜单上那些 star 数在这里不参与判断。
>
> 数据快照 2026-11-13。star 数取自 GitHub API，其余全部由 `uplift probe` 现跑。

## 怎么评的

三个探针，零模型调用，一条命令几秒钟：

| 探针 | 给出什么 |
|---|---|
| `static-cost` | 包内 token、会进上下文的 token、最大单技能、超预算比例、重复内容 |
| `skill-shape` | 技能的写法：frontmatter、description 长度、正文长度、按需加载比例 |
| `uninstall-clean` | 装完再卸，环境是否真的干净 |

四个口径要分清，混用会得出相反结论。

- `pkg tokens`：包里所有文本，含随包脚本。这是磁盘成本。
- `ctx tokens`：真正会进上下文的那部分（`.md/.json/.yaml/.txt`），脚本不算。
- `largest skill`：单个技能被激活时最多塞进去多少。预算按这个判，多技能包看最大的那个，单技能包看整包。
- `catalog`：所有技能的 description 之和。一个技能都不激活，这笔账也要付，因为目录里得列出它们。

没有跑 Tier 1，因为三臂对照要任务集、要模型、要钱，而且它测的是「技能 × 题」的联合效应。
写法缺陷不用花那个钱就能看见，先看结构，再决定值不值得跑分。

## 写得好的那几个

### 整包 644 token

`multica-ai/andrej-karpathy-skills`，232.7k star，一个技能，正文 573 token。

```
description: Behavioral guidelines to reduce common LLM coding mistakes.
             Use when writing, reviewing, or refactoring code to avoid overcomplication,
             make surgical changes, surface assumptions, and define verifiable success criteria.
```

644 token 意味着 10k 预算里能同时开 15 个这样的技能。它的 description 做了一件事：把「什么时候该用」
写成了触发条件，而不是「我是什么」。目录里模型看到的就是这句话，它写得像条件，才可能被想起来。

内容也不是知识，是行为准则。这类技能不需要检索，不需要 references，短就是对的。

### 正文 1.5k，长尾放 references

`obsidianmd/obsidian-skills` 里的 `obsidian-bases`，正文 1.5k，技能合计 6.3k。

```
description: Create and edit Obsidian Bases (.base files) with views, filters, formulas, and summaries.
             Use when working with .base files, creating database-like views of notes,
             or when the user mentions Bases, table views, card views, kanban boards, filters, or formulas.
```

正文给五步工作流，「函数参考」放进 `references/FUNCTIONS_REFERENCE.md`（1.9k），正文里说明什么时候去读。
常用路径短，长尾按需取。

### 39 个技能，正文中位 875

`mattpocock/skills`。39 个技能听起来像灾难，但每个都很薄，目录成本 1,390 token。

对照 `affaan-m/ECC`：47 个技能，目录成本 2,375 token，按需加载只有 6%。
多技能本身不是问题，每个都胖、目录里还塞正文，才是问题。

## 用不了的那几个

### 一个技能 409k，其中 113k 是一个 JSON

`Nutlope/hallmark` 单技能 409,006 token，`scripts/photos.json` 一个文件 113,128。
`cloudflare/security-audit-skill` 单技能 79,967，三个 `.cjs` 校验脚本各 7 到 9k。

这不叫写得差，叫放错地方。数据文件和校验脚本不需要进上下文，但它们在技能目录里，
任何一次「读这个技能目录」都可能把它们带进来。预算 10,000，这两个包分别是 41 倍和 8 倍。

改起来很便宜：数据文件移出技能目录，脚本改成调用而不是内联，正文只留「什么时候跑哪个脚本」。

### 菜单先吃掉 2,375 token

`affaan-m/ECC`，47 个技能。目录里每个技能要一段 description，加起来 2,375 token，
在你一个技能都没激活时就已经花掉了，相当于把预算的四分之一用来列菜单。按需加载比例只有 6%，
几乎所有内容都在正文里。

同一批数据里，`karpathy` 的目录成本是 55 token。差 43 倍。

### 单个技能 526k

`anthropics/skills` 里的 `claude-api`。SKILL.md 本身 26k，它引用的 `shared/model-migration.md` 一个文件 87k，
整个技能合计 526,405，是预算的 52 倍。

SKILL.md 里确实写了「按需读哪个文件」，这是对的。问题是没有机制保证 agent 只读需要的那一段：
一条 `Read` 就可能把 87k 全吃进来。参考库型技能都得面对这个取舍，这也是 `largest skill` 这一栏存在的理由。

## 一个例外：检索型技能

`GoogleChrome/modern-web-guidance-src` 那一行最吓人：1,265,943 token，超预算 5504%。

它是检索型技能。正文只有 2,444 token，知识库在包里，靠 `npx modern-web-guidance search/retrieve` 按需取。
1.26M 是磁盘成本，不是上下文成本。

所以看这一栏要看 `largest skill`，不看 `pkg tokens`。把两者混为一谈是这类评测最容易犯的错，
也是这张表里唯一需要人工判断的地方。

> 一处要交代的错位：`results/modern-web-guidance-src.json` 这张卡过去 Tier 0 探的是仓库里
> `.agents/skills`（13 个开发用技能，71k token），而 Tier 1 三臂测的是 `guides/`（就是本节说的知识库）。
> 两个都是真实产物，但不是同一个东西。2026-11-13 已把 manifest 指到 `guides`，两边描述同一个对象。

## 六条写法，可以直接照做

1. 正文 ≤ 2k token。中位数 875 的那批是好例子，超过 5k 就要问一句为什么不能拆。
2. description 写触发条件，不写自我介绍。用 "Use when …" 起句，60 到 120 token。目录里只有这句话。
3. 大知识放 `references/`，正文里写清什么时候读哪个文件。`obsidian` 和 `mattpocock` 都这么做。
4. 技能数 ≤ 10。目录成本等于所有 description 之和，47 个技能光菜单就 2.4k token。
5. 一个技能只干一件事。`karpathy-guidelines` 只给行为准则，连例子都不放。
6. 别把数据文件和校验脚本放技能目录。`photos.json` 那 113k 是最典型的误伤。

## 复现

```bash
git clone --depth 1 https://github.com/multica-ai/andrej-karpathy-skills /tmp/ks
node dist/cli.js probe /tmp/ks/skills --only static-cost,skill-shape,uninstall-clean

# 一次评一批
node dist/cli.js probe <pkg> --only static-cost,skill-shape --format json --out .uplift/review/<id>.json
node tools/review-table.mjs --md
```

`skill-shape` 是这一版新加的探针（`src/probes/skill-shape.ts`），报四件事：frontmatter 覆盖率、
有没有 description、description 的 token 中位数、按需加载比例。都是写作习惯，不需要模型就能测。

## 这套评测测不到什么

内容对不对，测不到。一个结构完美、内容空洞的技能，在这张表上会很好看。内容能不能提分只有三臂能回答，
见 `docs/15` 和 `docs/16`。

star 与效果的关系，也测不到。表里有 302k 星的包目录成本 2.4k，也有 233k 星的包只花 55 token。
星数是注意力，不是效果。

我们不给任何包下「坏」的结论。只报可测的事实：一激活超预算多少、目录占多少、能不能干净卸载。
要不要改、值不值得改，是作者的事。
