# 17 · 横向评测：12 个技能包，为什么有的能用、有的一激活就爆预算

> 这一篇不测「内容对不对」，只测**写法与成本**——这两件事不需要模型就能看清楚，
> 而且它们决定了一个技能包有没有机会起作用。榜单上那些 star 数，在这里不参与任何判断。
>
> 数据快照：2026-11-13。star 数取自 GitHub API，其余全部由 `uplift probe` 现跑。

---

## 一、怎么评的

只用三个**零模型调用**的 Tier 0 探针，一条命令、几秒钟、$0：

| 探针 | 给出什么 |
|---|---|
| `static-cost` | 包内 token、会进上下文的 token、最大单技能、超预算比例、重复内容 |
| `skill-shape`（本版新增） | 技能的**写法**：frontmatter、description 长度、正文长度、按需加载比例 |
| `uninstall-clean` | 装完再卸，环境是否真的干净 |

三个口径必须分清，混用会得出相反结论：

- **pkg tokens**：包里所有文本（含随包脚本）。这是**磁盘成本**。
- **ctx tokens**：真正会进上下文的那些（`.md/.json/.yaml/.txt`）。脚本不算。
- **largest skill**：单个技能被激活时最多塞进去多少。**预算按这个判**——多技能包看最大那个，单技能包看整包。
- **catalog**：所有技能的 description 之和。**一个技能都不激活，这笔账也要付**，因为目录里得列出它们。

为什么不用 Tier 1：三臂对照要任务集、要模型、要钱，而且它测的是「技能 × 题」的联合效应。
写法缺陷不用花那个钱就能看见——先看结构，再决定值不值得跑分。

## 三、三种「好」

### 好 1：小到可以一直开着 —— `karpathy-guidelines`，644 token

```
description: Behavioral guidelines to reduce common LLM coding mistakes.
             Use when writing, reviewing, or refactoring code to avoid overcomplication,
             make surgical changes, surface assumptions, and define verifiable success criteria.
```

644 token 意味着：**在 10k 预算里可以同时开 15 个这样的技能**。
而它的 description 干了一件事——把「什么时候该用」写成了触发条件，而不是「这是什么」。
技能目录里，模型看到的就是这句话；它写得像条件，才可能被想起来。

**它的内容也不是知识，是行为准则。** 这类技能不需要检索、不需要 references，短就是对的。

### 好 2：短正文 + 按需 references —— `obsidian-bases`，正文 1.5k、总 6.3k

```
description: Create and edit Obsidian Bases (.base files) with views, filters, formulas, and summaries.
             Use when working with .base files, creating database-like views of notes,
             or when the user mentions Bases, table views, card views, kanban boards, filters, or formulas.
```

正文 1.5k 给工作流（五步），把「函数参考」放进
`references/FUNCTIONS_REFERENCE.md`（1.9k），正文里说明什么时候去读。
这是**按需加载**的正确形状：常用路径短，长尾按需取。

### 好 3：技能很多，但每个都很小 —— `mattpocock/skills`，39 个技能、正文中位 875 tok

39 个技能听起来像灾难，但它正文中位只有 **875 token**，目录成本 1,390 tok。
对照 ECC：47 个技能、目录成本 **2,375 tok**、按需加载只有 6%。

**多技能不是问题，「每个都很胖 + 目录塞正文」才是问题。**

## 四、三种「用不了」

### 差 1：巨石单文件 —— `hallmark` 409,006 token、`security-audit-skill` 79,967

`hallmark` 一个技能 409k token，其中 `scripts/photos.json` 一个文件就 113,128 token。
`security-audit-skill` 一个技能 80k，三个 `.cjs` 校验脚本各 7–9k。

它们不是「写得不好」，是**放错了地方**：数据文件和校验脚本不需要进模型上下文，
但它们在技能目录里，于是任何一次「读这个技能目录」都可能把它们带进来。
预算是 10,000——这两个包分别是 41 倍和 8 倍。

**改法很便宜**：数据文件移到仓库外、脚本改成调用而不内联、正文只留「什么时候跑哪个脚本」。

### 差 2：目录成本失控 —— `ECC` 47 个技能、catalog 2,375 token、按需加载 6%

目录里每个技能要一段 description。47 个技能 = 2,375 token **在你一个技能都没激活时就已经花掉了**，
相当于把预算的四分之一用来「列出菜单」。而它的按需加载比例只有 6%——几乎所有内容都在正文里。

同一批数据里，`karpathy` 的目录成本是 55 token。**差 43 倍。**

### 差 3：把参考库当技能 —— `anthropics/skills` 的 `claude-api`，单技能 526,405 token

这不是「写坏了」，而是**风险没有被标出来**：
`claude-api/SKILL.md` 只有 26k，但它引用的 `shared/model-migration.md` 一个文件 87k，
整个技能合计 526k——**52 倍预算**。

SKILL.md 里确实写了「按需读哪个文件」，这是对的。问题是**没有任何机制保证 agent 只读它需要的那一段**：
一条 `Read` 就可能把 87k 全吃进来。这就是「参考库型技能」必须面对的取舍，也是 `largest skill` 这一栏存在的理由。

## 五、一个必须说清的例外：检索型技能

`GoogleChrome/modern-web-guidance-src` 那一行看起来最吓人：**1,265,943 token、超预算 5504%**。

但它是**检索型**技能：正文只有 2,444 token（`largest skill` 那一栏），
真正的知识库在包里，靠 `npx modern-web-guidance search/retrieve` 按需取。
换句话说 **1.26M 是磁盘成本，不是上下文成本**。

所以我们看这一栏时，看的是 **largest skill** 而不是 pkg tokens。
把这两者混为一谈，是这类评测最容易犯的错——**也是我们这张表里唯一需要人工判断的地方。**

> **一处必须交代的错位**：`results/modern-web-guidance-src.json` 这张卡上的 Tier 0 探的是
> 仓库里的 `.agents/skills`（13 个开发用技能，71k token），而 Tier 1 的三臂测量用的是 `guides/`
> （就是本节说的检索型知识库）。两个都是真实存在的产物，但不是同一个东西。
> 这是我们在早期没有把「测哪个表面」写死留下的债，2026-11-13 记在这里；
> 下一轮要么统一到 `guides/`，要么把两张卡分开出。
> **在这之前，引用这张卡的 Tier 0 数字时请注明它测的是 `.agents/skills`。**

## 六、好技能的六条写法（可以直接照做）

1. **正文 ≤ 2k token。** 中位数 875 的那批就是好例子；超过 5k 就要问「为什么不能拆」。
2. **description 写触发条件，不写自我介绍。** 用 "Use when …" 起句，60–120 token。
   目录里只有这句话，它写得不像条件，就永远不会被想起来。
3. **大知识放 `references/`，正文里写清「什么时候读哪个文件」。**
   这是唯一被证明有效的「按需加载」形状（`obsidian`、`mattpocock` 都这么做）。
4. **技能数 ≤ 10。** 目录成本 = 所有 description 之和，47 个技能光菜单就 2.4k token。
5. **一个技能只干一件事。** `karpathy-guidelines` 只给行为准则，连例子都不放。
6. **别把数据文件和校验脚本放技能目录。** `photos.json` 那 113k 是最典型的误伤。

## 七、复现

```bash
# 1. 把感兴趣的包浅克隆下来（任意目录）
git clone --depth 1 https://github.com/multica-ai/andrej-karpathy-skills /tmp/ks

# 2. 跑三个零模型探针
node dist/cli.js probe /tmp/ks/skills --only static-cost,skill-shape,uninstall-clean

# 3. 一次评一批，出成表
node dist/cli.js probe <pkg> --only static-cost,skill-shape --format json --out .uplift/review/<id>.json
node tools/review-table.mjs --md
```

`skill-shape` 是这次新加的探针（`src/probes/skill-shape.ts`），它报四件事：
frontmatter 覆盖率、有没有 description、description 的 token 中位数、按需加载比例。
这些都是**写作习惯**，不需要模型就能测，也不该等到跑完一晚模型才发现。

## 八、这套评测测不到什么

- **不测内容对不对。** 一个结构完美、内容空洞的技能，在这张表上会很好看。
  谁的内容真能提分，只有 Tier 1（三臂对照）能回答，见 `docs/15`、`docs/16`。
- **不测 star 与效果的关系。** 表里有 302k 星的包目录成本 2.4k，也有 232k 星的包只花 55 token。
  星数是注意力，不是效果。
- **不对任何一个包下「坏」的结论。** 我们只报可测的事实：一激活就超预算多少、目录占多少、能不能干净卸载。
  要不要改、值不值得改，是作者的事。
