# 00 · 为什么做 UpliftBench

## 一、一个荒谬的空白

2026 年 10–11 月，GitHub Trending 出现了一个从未有过的现象：**技能包（SKILL.md）成了最大的单一品类**。

我们在 30 天窗口内抓到 135 个上榜仓库，其中约 19% 是技能包，而且：

- Anthropic 发了 `anthropics/skills`、`claude-plugins-official`、`knowledge-work-plugins`
- Google 发了 `google/skills`、`android/skills`（Kotlin）、Chrome 发了 `modern-web-guidance-src`
- Cloudflare 发了 `security-audit-skill`（连续 7 天上榜）
- NVIDIA 发了 `SkillSpector`（扫技能包的技能包）
- Meta 发了 `astryx`（agent-ready 设计系统）
- AWS 发了 `agent-toolkit-for-aws`
- 个人作者：`addyosmani/agent-skills` **116,785 星**、`mattpocock/skills`、`obra/superpowers`、`K-Dense-AI/scientific-agent-skills`（177 个技能）

**然后，这一整个品类没有一个可信的效果数字。**

具体到三个最刺眼的事实：

| 事实 | 数据 |
|---|---|
| 星数最高的技能包拿不出任何效果数字 | `addyosmani/agent-skills` 116,785★，README 里 0 个 uplift 数值 |
| 唯一公开数字的技能包，靠这个数字登顶 | `GoogleChrome/modern-web-guidance-src`，+27~36pp uplift 表，11-13 当天 Trending 第 1 |
| 卖「可验证」的技能包，自己没被验证 | `cloudflare/security-audit-skill` 卖点原文 "independently verified, machine-readable findings" |

**这就是空白：技能包是纯 Markdown，改动零成本，所以数量会爆炸；但没人知道哪个真有用。**

## 二、为什么这个空白是「机会」而不是「陷阱」

### 2.1 需求侧已被证明

`GoogleChrome/modern-web-guidance-src` 用一个 uplift 表格拿到 Trending 第 1 名。这不是巧合——**在一个所有项目都自称有用的品类里，唯一给出可验证数字的那个，会自动获得全部注意力。**

### 2.2 供给侧为零（且官方不会做）

- 技能包作者不会给自己做基准：他们有动机美化，没动机揭短。
- 官方不会做第三方中立基准：Anthropic 做技能，做「给所有技能（含竞品）打分」的榜会失去中立性。
- 研究者做了（SkillsBench），但它是**封闭题库的学术基准**，不是**面向生态的审计工具**（见 `01-竞争格局.md`）。

**中立性是我们的护城河。**

### 2.3 成本极低

不需要 GPU，不需要训练，不需要模型权重。

第一版核心 = `git worktree` + 子进程 + 一张表 + 一个 SVG。

一个人一周能出可用的东西。

### 2.4 天然传播

- 每个技能包作者都想知道自己多好 → 会来跑
- 跑完想贴 badge → 传播
- 贴了 badge 就有人问「这什么」→ 引流
- 有争议的数字 → 讨论 → 更多传播

`MWG` 已经证明了 `badge + 数字` 是这个品类的传播公式。

## 三、这个项目到底解决什么问题（精确表述）

**不是**「技能好不好」——那是主观的、无法统一的。

**是**「这个技能相对一个等量安慰剂，额外贡献了多少可测量的效果」。

三个必须同时回答的子问题：

1. **净增益多少？** —— 三臂对照，剥离「多塞 token 本身有效」的混淆
2. **代价是什么？** —— token 开销、延迟、负迁移（装了它以后无关任务是否变差）
3. **安全吗？** —— 它有没有夹带隐藏指令、数据外泄、危险命令

第 1 条需要题库（Tier 1），第 2、3 条**不需要题库**（Tier 0），这就是为什么我们能覆盖任意技能包而 SkillsBench 不能。

## 四、为什么「统一 benchmark」这个说法本身是错的

第一反应会是：技能那么宽泛（安全审计 vs 设计 vs 求职 vs 紫微斗数），怎么统一？

**答案：不要统一「题」，要统一「测法」。**

临床试验没有统一「病」——心脏病和抑郁症的终点指标完全不同——但**同一套试验协议**（随机、对照、盲法、样本量、预设终点）同时管住了它们。

对应到我们：

| 层 | 是否统一 | 内容 |
|---|---|---|
| 协议层 | **统一（不可变）** | 三臂对照、同模型同版本、N≥3、统一计量口径、统一失败分类、必须报方差 |
| 任务集层 | **联邦（可插拔）** | 每个领域一套 `taskset.json`，版本化 + commit 哈希 + 镜像固定 |
| 评分器层 | **可插拔，但必须公开** | `tests` / `exact` / `rubric`（judge 模型固定）/ `visual-diff` / `human` |

**任务集是「声明」出来的，不是「统一」出来的。** 作者声称技能解决什么，就得交一套能验证那个声称的题。交不出来 → 不上榜，而不是给个假分数。

## 五、跨领域可比的技巧：归一化到「剩余空间」

不同领域的绝对分没法比，但「填掉了多少剩余空间」可以比：

```
uplift_pp       = guided − baseline                      # 绝对提升（百分点）
headroom_closed = (guided − baseline) / (1 − baseline)   # 归一化：填掉多少剩余空间
```

| 领域 | baseline | guided | uplift | headroom closed |
|---|---|---|---|---|
| 安全审计（命中注入漏洞率） | 20% | 60% | +40pp | **50%** |
| 设计技能（rubric 100 分制） | 40 | 70 | +30pp | **50%** |

同一个 50%，一个来自漏洞命中，一个来自审美评分。**这就是跨领域可比性的来源。**

**但必须同时报绝对值**：baseline 95% 时 headroom 只剩 5%，+4pp 就是 80% closed，数字好看但毫无意义。

## 六、为什么必须有安慰剂臂（本项目的核心差异点）

这是本项目**唯一不可让步**的设计。

**问题**：往上下文里多塞 12,000 token 的技能包，本身就会改变模型行为——可能让它更谨慎、更啰嗦、更遵守格式。这些变化**与技能内容无关**。

只做「无技能 vs 有技能」两臂，测到的是：

```
观测差异 = 技能真实效果 + 「多塞了 token」的效果 + 噪声
```

**安慰剂臂就是用来减掉中间那一项的**：

```
净效果 = treatment − placebo
```

这是医学和因果推断的标准做法（uplift modeling 的原始定义）。已有基准（含 SkillsBench）全部只做两臂，所以它们的数字里混着这个混淆项。

**这是我们的第一个、也是最硬的一个差异化。**

## 七、成功长什么样

**6 个月后，如果这个项目成功了：**

1. 技能包 README 里的 badge 变成常态，就像 CI badge 一样
2. 「这个技能的 uplift 是多少」成为作者必须回答的问题
3. 有作者因为被测出负迁移而改进技能包
4. 有人引用我们的协议去做自己的领域任务集

**失败的样子：**

1. 只做了 Tier 1，变成 SkillsBench 的劣质复刻
2. 安慰剂臂因为「太麻烦」被砍掉，退回两臂
3. 榜单被大厂技能包占据，个人作者觉得不公平而离开
4. 我们开始发自己的技能包，中立性崩塌
