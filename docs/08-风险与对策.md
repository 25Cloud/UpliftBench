# 08 · 风险与对策

> 按「发生概率 × 杀伤力」排序。

---

## 风险 1：SkillsBench 加安慰剂臂（概率高，杀伤力最大）

**情景**：他们已经证明了配对评测，加第三个臂是自然下一步。

**对策**：
1. **不跟他们比题库，比覆盖面。** 他们的 87 题是封闭的，我们覆盖真实发布的技能包。
2. **不跟他们比论文，比自助服务。** 作者能自己跑出 badge，他们做不到。
3. **主动引用、主动合并。** 如果他们加了三臂，我们就把重点转到 Tier 0 + 联邦 + 安全维度，并公开说「效果维度参考 SkillsBench」。
4. **最终形态是互补而非竞争**：他们是「技能效果的学术基准」，我们是「技能包的审计与分发基础设施」。

**底线判断**：只要「中立 + 自助 + 覆盖真实包」三条成立，我们就有位置。

---

## 风险 2：任务集太贵，跑不动（概率高，杀伤力中）

**情景**：`--repeats 3 × 3 臂 × 87 题` = 783 次跑，成本爆炸。

**对策**：
1. **默认 30 题小集**，全量作为可选。
2. **分层抽样**：easy/medium/hard 各 10 题，保证区分度。
3. **`--max-cost` 硬闸**，默认 $10，超过即停并保留数据。
4. **Tier 0 免费**（不调模型的部分），Tier 1 才花钱。
5. **交错执行**降低重跑需求（方差小 → 重复次数可以少）。

---

## 风险 3：harness 不暴露技能激活事件（概率高，杀伤力中）

**情景**：`trigger-precision` 和 `constraint-following` 需要知道「哪个技能被激活」，多数 harness 不提供。

**对策**：
1. **老实标 `supported: false`**，绝不编数字。
2. 优先支持 Claude Code（有 hooks 事件系统）。
3. 对不支持的 harness，用**代理指标**：注入的技能内容是否出现在上下文中（可从 transcript 检测），并明确标注这是代理指标。
4. 在文档里公开支持矩阵，让用户知道哪些能测。

---

## 风险 4：安慰剂臂被质疑「你构造的安慰剂不公平」（概率中，杀伤力大）

**情景**：作者会说「你的安慰剂文本质量太差/太好，所以我的 uplift 被高估/低估」。

**对策**：
1. **安慰剂构造规则完全公开且可复现**（`docs/02 §1.2`），种子由技能包内容哈希决定。
2. **提供 `--placebo <file>`**，允许作者自带安慰剂，但必须在 SkillCard 里标注 `placebo: custom`，且**不参与主榜排名**。
3. **公开 `placebo_effect_pp`**，让所有人自己判断。
4. **做敏感性分析**：同一技能包用 3 种不同安慰剂各跑一遍，报 uplift 的范围。如果范围很宽，说明结论不稳，这本身是有价值的信息。

---

## 风险 5：数字被断章取义（概率高，杀伤力中）

**情景**：某技能包被贴上 `uplift -2%` 的 badge，作者不满，公关危机。

**对策**：
1. **badge 默认只显示 headroom 和样本量，不显示负值红色**，负值用灰色显示「no measurable gain」而非「-2%」。
2. **提供申诉通道**：作者可提交自己的任务集，我们跑，结果并列显示。
3. **永远附置信区间**。`-2pp, CI [-9, +5]` 和 `-2pp, CI [-3, -1]` 是完全不同的结论。
4. **文档里明确**：「本榜测量的是特定任务集上的净增益，不代表技能包的整体价值」。

---

## 风险 6：Windows 兼容性（概率高，杀伤力低）

**情景**：开发机是 Windows，worktree 路径、子进程 shell、文件锁都会出问题。

**对策**：
1. **从 D1 就在 Windows 上测**，不要最后才适配。
2. worktree 路径用 `path.join`，不拼字符串。
3. 子进程统一用 `execa`，它会处理 shell 差异。
4. SQLite 用 `better-sqlite3`（有预编译二进制），避免 node-gyp。
5. CI 跑 Windows + Linux 双平台。

---

## 风险 7：中立性被自己破坏（概率中，杀伤力致命）

**情景**：为了增长，我们开始发自己的技能包，或者给赞助商技能包优待。

**对策**：
1. **写进宪法**：UpliftBench 永不发布自己的技能包（`AGENTS.md §1.5`）。
2. **赞助商不参与排名**，只出现在页面底部。
3. **协议和任务集全部开源**，任何人可 fork 重跑。
4. **公开所有原始数据**（`runs.db` 可导出）。

---

## 风险 8：Tier 0 被当成「分数」误用（概率中，杀伤力中）

**情景**：用户看到「静态开销 12,400 tok ⚠️」就认为这个技能包不好。

**对策**：
1. **Tier 0 输出的是 facts 不是 scores**，UI 上不给总分、不给等级。
2. 卡上明确写「Tier 0 测量事实，Tier 1 测量效果」。
3. 不提供 Tier 0 的排行榜，**只提供查询**。
4. 文档里反复强调：token 多不等于差，要看 uplift。

---

## 风险 9：命名冲突（概率低，杀伤力低）

**现状**：GitHub 有 2 个同名仓库（`Aman12x/UpliftBench` 1★、`TirtheshJani/UpliftBench` 0★，都是营销增益模型），npm/PyPI/域名全空。

**对策**：
1. 组织名用 `upliftbench`（GitHub org），仓库名 `upliftbench/upliftbench`。
2. CLI 命令 `uplift`，需检查是否与其他工具冲突（目前未见）。
3. 首次发布时在 README 顶部加一句区分说明。
4. 如果冲突加剧，备选名：`Touchstone`（试金石）。

---

## 风险 10：没人用（概率中，杀伤力大）

**情景**：做出来了，但技能包作者不在乎。

**对策**：
1. **先自己用**：D7 对 5 个热门技能包出卡，主动发给作者（PR 加 badge）。
2. **GitHub Action 是最强分发**：作者在 PR 里看到效果变化，比榜单有效 10 倍。
3. **数字要能一句话说完**：`uplift 31%` 比 `headroom_closed 0.564` 好传播。
4. **制造对比**：两臂 vs 三臂实验、MWG 交叉验证，这两个都是有传播力的内容。
