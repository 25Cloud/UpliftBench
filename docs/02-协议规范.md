# 02 · 协议规范（Protocol Spec）

> **这是本项目的宪法。代码服从它，不许反过来改定义迁就实现。**
> 版本：`protocol/1.0.0`（任何破坏性修改必须升 major 并在 CHANGELOG 记录）

---

## 一、三臂设计（Three-Arm Design）

任何 `uplift` 数字必须来自三臂对照，缺一不可。

| 臂 | 代号 | 条件 | 目的 |
|---|---|---|---|
| 对照 | `baseline` | 不装任何技能 | 基准水平 |
| 安慰剂 | `placebo` | 装**等 token 量**的中性文本 | 剥离「多塞 token 本身有效」的混淆 |
| 处理 | `treatment` | 装真实技能包 | 观测水平 |

### 1.1 净效果定义

```
uplift_pp       = pass_rate(treatment) − pass_rate(placebo)
headroom_closed = (pass_rate(treatment) − pass_rate(placebo)) / (1 − pass_rate(placebo))
```

**注意：是减去 `placebo`，不是减去 `baseline`。**

减去 `baseline` 得到的量必须单独报告，并标记为未校正：

```
raw_gain_pp = pass_rate(treatment) − pass_rate(baseline)    # 未校正，不得单独进榜单
placebo_effect_pp = pass_rate(placebo) − pass_rate(baseline) # 安慰剂效应本身，有独立信息价值
```

`placebo_effect_pp` 不是噪声——**它本身就是一个有价值的指标**：它衡量「这个技能包的长度值多少分」。一个 `placebo_effect_pp` 很大的技能包，说明它的分数可能主要来自「上下文变长了」。

### 1.2 安慰剂构造规则（硬约束）

安慰剂文本必须满足：

1. **token 量相等**：`|tokens(placebo) − tokens(treatment)| / tokens(treatment) ≤ 2%`
2. **语义中性**：不得包含任何与任务领域相关的指令、术语、格式要求
3. **结构相似**：同样有标题层级、同样有列表（避免「有结构 vs 无结构」的混淆）
4. **确定性**：同一技能包每次生成同一个安慰剂（用内容哈希做种子）

**推荐做法**：取技能包的 token 数 N，用一份固定的中性语料（例如通用软件工程常识的平铺叙述）截取到 N token，按技能包的标题结构重新排版。

**禁止做法**：
- 用「你是一个乐于助人的助手」这类短句（长度差太多）
- 用其他领域的技能包（引入领域混淆）
- 用随机词（破坏语言自然性，模型行为会异常）

## 二、执行约束（不可协商）

| 约束 | 要求 | 原因 |
|---|---|---|
| 模型版本 | 三臂必须**同一个精确版本**（不是 `latest`） | 跨版本不可比 |
| 温度 | 固定，且记录 | 影响方差 |
| seed | 固定，且记录；不支持 seed 的 harness 必须标注 | 可复现性 |
| 重复次数 | `N ≥ 3`，建议 5 | 报方差需要 |
| 环境 | 同一 docker 镜像哈希 / 同一 commit | 排除环境漂移 |
| 顺序 | 三臂**交错执行**（b,a,c,a,b,c...），不是先跑完一臂再跑下一臂 | 排除时间漂移（API 限速、服务降级） |
| 任务顺序 | 每臂内任务顺序**随机化**，种子固定 | 排除顺序效应 |

**交错执行这一条最容易被忽略，但它是廉价且有效的方差控制手段。**

## 三、指标定义（完整清单）

### 3.1 效果类

| 字段 | 定义 | 单位 |
|---|---|---|
| `pass_rate` | 通过任务数 / 总任务数 | 0–1 |
| `uplift_pp` | `pass_rate(treatment) − pass_rate(placebo)` | 百分点 |
| `headroom_closed` | `uplift_pp / (1 − pass_rate(placebo))` | 0–1 |
| `raw_gain_pp` | `pass_rate(treatment) − pass_rate(baseline)` | 百分点（未校正） |
| `placebo_effect_pp` | `pass_rate(placebo) − pass_rate(baseline)` | 百分点 |
| `ci95` | 三臂差值的 95% 置信区间 | 百分点 |

### 3.2 代价类

| 字段 | 定义 |
|---|---|
| `tokens_in_total` / `tokens_out_total` | 全部任务的输入/输出 token 合计 |
| `token_overhead_pct` | `(tokens_in(treatment) − tokens_in(baseline)) / tokens_in(baseline)` |
| `wall_time_p50` / `wall_time_p95` | 单任务耗时中位数/95 分位 |
| `tool_calls_mean` | 单任务平均工具调用次数 |
| `cost_usd_total` | 按公开价目折算的总成本 |

### 3.3 稳定性类

| 字段 | 定义 |
|---|---|
| `pass_rate_std` | 跨重复的标准差 |
| `flaky_tasks` | 同一臂内跨重复结果不一致的任务列表 |
| `determinism_gain` | `std(baseline) − std(treatment)` —— 技能是否让行为更稳定（正数=更稳） |

### 3.4 失败分类（统一 taxonomy）

每个失败任务必须归入且仅归入一类：

| 代号 | 含义 |
|---|---|
| `wrong_answer` | 给出了答案但错 |
| `gave_up` | 明确放弃 / 声称无法完成 |
| `hallucinated` | 编造了不存在的事实/API/文件 |
| `constraint_violated` | 违反了任务或技能的硬约束 |
| `broke_something` | 破坏环境（改坏文件、删数据、死循环） |
| `timeout` | 超时 |
| `tool_error` | 工具调用失败且未恢复 |
| `grader_error` | 评分器自身报错（不计入 pass_rate，单独统计） |

**`grader_error` 必须单独报告。把它算作失败是最常见的基准作弊方式。**

## 四、评分器分级（公信力的唯一来源）

| 等级 | 定义 | 可信度 | 允许进榜 |
|---|---|---|---|
| **A** | 可执行验证：测试通过、精确匹配、漏洞命中、构建成功 | 硬 | ✅ 主榜 |
| **B** | rubric + **固定版本** LLM judge（judge 模型与 prompt 必须公开） | 中 | ✅ 副榜（与 A 分组显示） |
| **C** | 人工抽检 / 众包 | 软 | ❌ 只做附录 |

**铁律：A 和 B 的数字不许并排排名，只能分组显示。C 级不进榜。**

理由：把 A 级（测试通过）和 B 级（LLM 觉得不错）混排，等于用不同尺子量身高再排名。

### 4.1 B 级评分器的额外要求

- judge 模型精确版本号写进 `taskset.json`
- judge prompt 全文公开
- 必须报告 judge 与人工的一致性（至少 30 个样本，报 Cohen's κ）
- κ < 0.6 的 B 级评分器**降级为 C**

## 五、归一化与可比性

### 5.1 为什么需要归一化

| 领域 | baseline | guided | uplift_pp | headroom_closed |
|---|---|---|---|---|
| 安全审计 | 20% | 60% | +40 | **50%** |
| 设计技能 | 40 | 70 | +30 | **50%** |

同一个 50%，跨领域可比。

### 5.2 归一化的失真区间（必须标注）

| 条件 | 问题 | 处理 |
|---|---|---|
| `baseline > 0.95` | headroom ≤ 5%，微小绝对变化被放大 | 强制同时报 `uplift_pp`；headroom 加 `⚠️低空间` 标记 |
| `baseline < 0.05` | 分母接近 1，归一化几乎等于绝对值 | 正常，但标注「近满空间」 |
| `N < 30` 任务 | 置信区间过宽 | 标注 `n<30`，不进主榜 |

## 六、报告格式（强制字段）

任何对外发布的 uplift 数字，必须同时给出：

```
uplift +18pp  |  headroom 41%  |  N=30  |  95%CI [9, 27]  |  A级  |  placebo_effect +6pp
```

缺任何一项，这个数字就是不合格的。

**`placebo_effect` 必须公开**——这是本项目区别于所有其他基准的地方，不能藏。

---

## 七、协议版本与兼容性

- 协议版本独立于软件版本，格式：`protocol/MAJOR.MINOR.PATCH`
- 新增可选字段 → MINOR
- 修改指标定义 / 三臂语义 → **MAJOR**（历史数据标记为不可比）
- 每个 SkillCard 必须写入它生成时的协议版本

## 八、反对意见预案

| 反对 | 回应 |
|---|---|
| 「安慰剂臂成本 ×1.5」 | 成本换公信力。且 Tier 0 不需要安慰剂臂（它是静态+行为探针，不是分数） |
| 「任务集太贵」 | 默认 30 题小集，全量作为付费/自托管选项 |
| 「不同领域不能比」 | 我们不比绝对分，比 `headroom_closed`，并强制同时报绝对值 |
| 「技能是主观的」 | 所以才有 A/B/C 分级。我们不假装 A 级能测审美，我们只测能测的 |
